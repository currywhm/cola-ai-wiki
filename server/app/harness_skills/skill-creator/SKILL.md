# 制作技能

## 目标
把用户的一句话需求，变成一套**下一轮能被直接加载、照着做就能交付**的技能包。
技能包是写给模型看的操作说明，不是写给人看的介绍文章：写清楚「做什么、按什么步骤、依据什么标准、输出成什么样」。

## 铁律
1. **不能只交一个 `SKILL.md`。** 一套技能包至少三个文件：`SKILL.md`、`references/` 下一个依据文件、`assets/` 下一个模板文件。
2. **本产品没有任何执行能力。** 不要写 `scripts/`，不要写需要运行的代码、命令或可执行文件，也不要让使用者去跑脚本；全部能力靠上面三份文档承载。
3. 三个文件分工不许混：
   - `SKILL.md`：只写流程（做什么、按什么步骤、输出成什么样），不堆标准细节。
   - `references/<名称>.md`：判断依据与标准（核对清单、口径定义、规范条文、对照表、常见错误），30-80 行。
   - `assets/<名称>.md`：可直接套用的输出模板，留 `{{占位符}}`，让使用者照着填就能成稿。
4. 目录名与 frontmatter 的 `name` 必须一致，且只能是**小写英文字母、数字、连字符**（例：`meeting-notes`）。中文名写进 `description`，**不要写进 `name`**：写成中文运行时不会加载这个技能包。

## 输出位置
- 技能包根目录由本轮任务要求给出（形如 `skills-build/<slug>`，相对当前工作目录）。
- 在该目录下写出：
  - `SKILL.md`
  - `references/<名称>.md`
  - `assets/<名称>.md`
- 不要写到别的位置，不要额外写 README、示例或脚本文件。

## SKILL.md 的结构
第一段必须是 frontmatter，三个字段都要有：

```
---
name: <小写英文短名，用连字符，如 meeting-notes>
description: <一句话说清这个技能做什么、产出什么，40 字以内>
whenToUse: <什么情况下该用这个技能，30 字以内>
---
```

frontmatter 之后按下面的顺序写正文，用小标题分节：

1. `# <技能名>`
2. `## 目标`：一段话，说清这个技能交付什么。
3. `## 前提与边界`：立场假设、资料不足时怎么写、哪些情况必须提示人工复核。
4. `## 执行步骤`：有序列表，每步一个动作，动词开头，能直接照做；需要判断依据时写明去看 `references/` 里的哪个文件。
5. `## 输出格式`：把要产出的结构写死（分几节、每节放什么），并指向 `assets/` 里的模板。
6. `## 注意事项`：边界与禁忌，例如不要编造什么、口径不明怎么办。
7. `## 附带文件`：逐个列出 `references/` 与 `assets/` 下的文件、用途、什么时候去读。
8. `## 自检`：至少 4 条，逐条写成「……了吗？」这样能核对真假的检查项。

## references/ 写什么
- 写**标准与依据**，不写流程：核对清单、口径定义、规范条文、对照表、常见错误。
- 要让 `SKILL.md` 的执行步骤能直接引用它，例如「对照 `references/风险清单.md` 的十二类条款逐类核对」。
- 条目化，能用表格就用表格；不要写「注意沟通」这类没有核对价值的话。

## assets/ 写什么
- 写**可直接复制的输出模板**：标题层级、小节名、表格表头、`{{占位符}}`。
- 模板要能一次套用就成稿；末尾加一行说明「未提供的字段保留占位符，不要编造」。

## 写的时候要守住
- **只写用户要的能力**，不要自动加用户没提的功能，不要扩展成平台。
- **步骤要具体到能执行**：写「按金额、账期、验收三条各列 3 条」，不要写「进行分析」。
- **输出格式要能直接套用**：宁可给骨架，也不要只描述风格。
- 用户需求里含糊的地方，按最合理的常见做法定下来并在「注意事项」里写明，不要反问也不要留空。
- 除 frontmatter 的 `name` 外，全部用简体中文。

## 完成后
用一句话说明你创建了哪个技能、包含哪些文件，不要粘贴 `SKILL.md` 全文。
